# 05 Technical Architecture

## 1. Назначение и границы

Документ определяет технические принципы и прорабатывает архитектурные решения, необходимые для реализации OpenDWH. Он наследует продуктовые ограничения из `04Product Architecture` и не пересматривает их:

- Модульный монолит, развёртывание на одном узле в MVP.
- PostgreSQL — системные данные и метаданные; Parquet — локальные копии.
- Единственный интерфейс потребления — REST GET.
- OAuth 2.0 Client Credentials и RBAC на уровне коллекций.
- Контроль нагрузки на исходные СУБД как обязательное требование.

Технические принципы:

- Одно развёртываемое приложение, управляемое через CLI.
- PostgreSQL — единственный источник истины о состоянии системы; Parquet — плоскость данных.
- Компоненты взаимодействуют только через явные интерфейсы и не разделяют изменяемое состояние.
- Спорные технические выборы фиксируются как ADR в `docs/adr/` с альтернативами и обоснованием; в тексте документа они помечены как отложенные решения.

## 2. Runtime Architecture

### Процессная модель

Вся система работает в рамках одного процесса. Используется асинхронная модель выполнения для I/O-операций — сетевые запросы, обращения к PostgreSQL и внешним СУБД. CPU-ёмкая работа с Parquet — кодирование, декодирование, сжатие — выделяется в отдельный пул потоков, чтобы фоновые синхронизации не блокировали обработку REST-запросов.

### Жизненный цикл запроса

1. API Server принимает REST GET-запрос.
2. Authentication проверяет Bearer-токен.
3. Authorization проверяет разрешение на целевую коллекцию.
4. Разрешается активная версия коллекции.
5. Query Engine выполняет запрос к данным версии.
6. Результат сериализуется и возвращается.

Версия фиксируется на входе запроса: публикация новой версии не переключает запрос посередине выполнения.

### Жизненный цикл синхронизации

1. Scheduler инициирует обновление коллекции или группы.
2. Sync Engine получает согласованный снимок данных из источника батчами.
3. Storage Engine записывает новую версию в Parquet.
4. Успешность операции фиксируется в PostgreSQL.
5. Выполняется атомарная публикация версии.
6. Операция записывается в историю.

### Конкурентность

Параллельно могут выполняться несколько REST-запросов и несколько синхронизаций в пределах лимитов из `04Product Architecture` §14. Изоляция рабочих нагрузок в MVP достигается лимитами ресурсов, а не разделением процессов. Что мешает распределённому развёртыванию на данный момент: локальное хранение Parquet и внутрипроцессное состояние планировщика. Это осознанное ограничение, а не недосмотр.

## 3. Storage Architecture

### PostgreSQL — плоскость управления

PostgreSQL хранит логические сущности системы: источники и параметры подключения, коллекции и описания SQL VIEW, версии коллекций, расписания и группы синхронизации, клиентов, роли и разрешения, историю операций, системные настройки. Любое состояние, которым управляет администратор, проходит через PostgreSQL.

### Parquet — плоскость данных

Локальные копии хранятся как набор файлов Parquet, организованный по коллекциям и версиям. Базовое соглашение: отдельный набор файлов на версию коллекции. Для небольших коллекций допустим один файл; для крупных — разбиение на части по диапазонам ключевого столбца. Конкретная схема партиционирования, размер row group и соглашения об именовании файлов — отложенное решение (см. §9): они существенно влияют на производительность чтения и требуют замеров.

### Жизненный цикл версии

Версия коллекции проходит состояния: подготовка → активная → архивная. Потребителям доступна только активная версия. Публикация выполняется в два действия: запись указателя активной версии в PostgreSQL и атомарное переключение на уровне файловой системы. Читатель либо видит прежнюю версию целиком, либо новую — частично записанные данные недоступны по построению. Политика хранения старых версий — отложенное решение.

## 4. Query Engine

Query Engine отвечает за выполнение фильтрации, сортировки, выборки полей и пагинации над активной версией коллекции.

Критерии выбора движка — по `04Product Architecture` §5: производительность аналитических запросов над набором данных в сотни миллионов записей, ограничение потребления памяти, конкурентный доступ читателей, возможность встраивания в Rust-рантайм, управляемость ресурсов.

Кандидаты:

| Критерий | DuckDB | Apache DataFusion |
|---|---|---|
| Зрелость аналитического исполнителя | Высокая, встраиваемая СУБД | Фреймворк построения исполнителей |
| Интеграция с Rust | Через C API и обёртки | Нативная, написан на Rust |
| Конкурентные читатели | Ограниченная модель | Зависит от построенной обвязки |
| Объём собственного кода | Минимальный | Существенный |

Оба варианта допускают встраивание в процесс OpenDWH; альтернатива «отдельный процесс-исполнитель» рассматривается и отклоняется на этапе MVP как лишний операционный контур. Окончательный выбор — отложенное решение, фиксируется в ADR после сравнительного исследования.

## 5. Synchronization Architecture

### Конвейер получения данных

Синхронизация строится как конвейер: чтение батча из источника → при необходимости преобразование типов → запись в файлы новой версии → контрольные точки прогресса в PostgreSQL. Контрольные точки позволяют возобновить прерванную загрузку без полного повторения.

### Согласованность снимка

Механизм согласованного снимка зависит от транзакционной модели источника: для PostgreSQL и Microsoft SQL Server применяются их нативные механизмы изоляции снимков. Конкретные режимы и их влияние на нагрузку источника уточняются при реализации коннекторов.

### Инкрементальное обновление

Три механизма в порядке возрастания точности и сложности: поле изменения записи (`updated_at` и аналоги), Change Tracking, CDC. Применимость каждого зависит от возможностей конкретной СУБД и структуры VIEW; при отсутствии надёжного механизма используется полная перезагрузка. Выбор механизма — настройка коллекции, а не глобальное решение.

### Контроль нагрузки

Ограничения из `04Product Architecture` §14 реализуются на уровне коннектора: размер батча, паузы между батчами, лимит одновременных синхронизаций на источник. Это позволяет держать нагрузку на production в заданных границах независимо от поведения потребителей.

## 6. Security Architecture

### Аутентификация

В MVP OpenDWH самостоятельно выполняет роль authorization server по OAuth 2.0 Client Credentials: регистрация клиента, выдача и валидация access token с ограниченным временем жизни. Детали реализации эмиссии токенов — отложенное решение.

### Авторизация

Проверка разрешений выполняется в единой точке — между разрешением коллекции и исполнением запроса. Правила RBAC хранятся в PostgreSQL. Новые проверки в других компонентах не вводятся, чтобы не размножать логику доступа.

### Секреты

Учётные данные подключений хранятся в PostgreSQL в зашифрованном виде. Ключ шифрования хранится отдельно от базы; компрометация PostgreSQL не раскрывает секреты. Конкретная схема шифрования и ротация ключей — отложенное решение. Интеграция с корпоративными Secret Manager рассматривается как развитие после MVP.

### Аудит

Обращения к данным фиксируются: клиент, коллекция, время, результат. История операций синхронизации ведётся в том же контуре.

## 7. Data Access Architecture

### Сопоставление API и данных

Каждая опубликованная коллекция предоставляет сгенерированный набор endpoints, доступных только на чтение. Маршрутизация происходит через метаданные коллекции, а не через конфигурацию API отдельно — API не может разойтись с состоянием хранилища по построению.

### Обработка запроса

Возможности запроса наследуются из `04Product Architecture` §11: фильтрация с вложенными условиями, сортировка, выбор полей, пагинация. Параметры запроса преобразуются в исполняемый план Query Engine над активной версией.

### Пагинация

Offset-пагинация применяется для небольших выборок. Курсорная пагинация — основной механизм для крупных коллекций: курсор передаётся как непрозрачный токен, кодирующий позицию в порядке сортировки. Формат токена — отложенное решение.

## 8. Наблюдаемость

Система ведёт структурированные логи с идентификаторами корреляции, позволяющими связать запрос, операцию синхронизации и ошибку. Метрики покрывают длительность операций и объёмы обработанных данных. История операций и статусы компонентов хранятся в PostgreSQL и доступны через CLI, как определено в `04Product Architecture` §15.

## 9. Открытые вопросы и следующие шаги

Открытые вопросы `04Product Architecture` §17 распределяются так:

| Вопрос | Где закрывается |
|---|---|
| Выбор Query Engine | ADR-0001, после сравнительного исследования |
| Физическая организация Parquet, формат версий | ADR-0002, после замеров прототипа |
| Механизм атомарной публикации | Разделы 2–3 данного документа, детали — в реализации |
| CDC и Change Tracking для поддерживаемых СУБД | Спайк на коннекторе каждой СУБД |
| Обнаружение изменений SQL VIEW | Спайк Schema Manager |
| Протокол и формат курсорной пагинации | Дизайн API, отдельный документ |
| Реализация OAuth 2.0, шифрование секретов | ADR по мере проработки Security Architecture |
| Стратегия ограничения нагрузки на production | Принципы §5, параметры — в реализации |

Следующие шаги: подготовить ADR-0001 (Query Engine) и ADR-0002 (организация Parquet и версионирование), провести спайки по инкрементальному обновлению.

**Основной принцип: состояние — в PostgreSQL, данные — в версионированных файлах Parquet, вычисления — в изолированном исполнителе, а спорные выборы — в ADR с явными альтернативами.**
