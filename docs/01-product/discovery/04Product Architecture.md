
## 1. Назначение

OpenDWH — On-Premise платформа для централизованного доступа к корпоративным данным через REST API.

Архитектура должна обеспечивать:

- Подключение к разнородным корпоративным СУБД.
    
- Получение данных из SQL VIEW.
    
- Создание и обслуживание локальных копий.
    
- Автоматическую генерацию REST API.
    
- Централизованное управление доступом.
    
- Контроль нагрузки на исходные системы.
    
- Обработку больших объёмов данных.
    
- Возможность дальнейшего горизонтального масштабирования.
    

## 2. Архитектурные ограничения

1. Только On-Premise.
    
2. Отсутствие зависимости от Cloud-сервисов.
    
3. Все корпоративные данные остаются внутри инфраструктуры организации.
    
4. PostgreSQL используется для системных данных и метаданных OpenDWH.
    
5. Parquet используется для хранения локальных копий данных.
    
6. REST GET является основным интерфейсом потребления данных.
    
7. SQL VIEW является основным механизмом определения доступных наборов данных.
    

## 3. Общая архитектура

Первая версия OpenDWH реализуется как модульный монолит.

Основные логические компоненты:

|Компонент|Ответственность|
|---|---|
|CLI|Управление системой|
|API Server|Обработка REST GET-запросов|
|Authentication|Аутентификация клиентов|
|Authorization|RBAC и проверка разрешений|
|Source Manager|Управление подключениями к источникам|
|Connector Engine|Взаимодействие с внешними СУБД|
|Schema Manager|Исследование и управление схемами SQL VIEW|
|Sync Engine|Получение и обновление данных|
|Scheduler|Планирование операций синхронизации|
|Storage Engine|Управление локальными копиями Parquet|
|Query Engine|Выполнение запросов к локальным данным|
|Observability|Статусы, история операций и ошибки|

Компоненты должны иметь чёткие границы ответственности, чтобы в дальнейшем отдельные части системы можно было выделить в самостоятельные сервисы.

## 4. Модель развёртывания

### MVP

Single-node.

Все компоненты работают в рамках одного узла инфраструктуры.

### Дальнейшее развитие

Архитектура должна допускать распределённое развёртывание и параллельную работу компонентов.

Целевой сценарий:

- Несколько администраторов.
    
- Множество параллельных потребителей.
    
- Несколько одновременно выполняющихся процессов синхронизации.
    

## 5. Модель хранения

OpenDWH использует два основных механизма хранения.

### PostgreSQL

Используется для хранения:

- Конфигурации источников.
    
- Метаданных коллекций.
    
- Описаний SQL VIEW.
    
- Схем данных.
    
- Пользователей и клиентов.
    
- Ролей и разрешений.
    
- API-конфигураций.
    
- Расписаний.
    
- Состояния синхронизации.
    
- Истории операций.
    
- Системных настроек.
    

### Parquet

Используется для хранения локальных копий корпоративных данных.

Преимущества выбранного подхода:

- Колонночное хранение.
    
- Сжатие данных.
    
- Поддержка аналитических сценариев.
    
- Независимость от исходной СУБД.
    
- Возможность использования различных движков обработки.
    

### Query Engine

Конкретный движок для работы с Parquet пока не выбран.

Кандидаты для исследования:

- DuckDB.
    
- Apache DataFusion.
    

Решение принимается после сравнительного исследования производительности, потребления ресурсов, конкурентного доступа и возможностей интеграции.

## 6. Работа с источниками

MVP должен поддерживать:

- Microsoft SQL Server.
    
- PostgreSQL.
    

Основной объект получения данных — SQL VIEW.

Процесс подключения:

1. Администратор регистрирует источник.
    
2. OpenDWH проверяет доступность подключения.
    
3. Schema Manager исследует доступные представления.
    
4. Администратор выбирает необходимые VIEW.
    
5. OpenDWH определяет структуру данных.
    
6. Администратор может вручную переопределить параметры схемы.
    
7. Выбранные представления регистрируются как коллекции.
    

## 7. Работа со схемами

Schema Manager отвечает за исследование структуры SQL VIEW и синхронизацию схем.

При обнаружении изменений:

- Новые поля.
    
- Удалённые поля.
    
- Изменённые типы данных.
    

OpenDWH должна обнаружить изменение и уведомить администратора.

Несовместимые изменения не должны автоматически заменять опубликованную схему API.

Предыдущая схема сохраняется до ручного переопределения или подтверждения изменений.

## 8. Модель синхронизации

Sync Engine отвечает за получение и обновление локальных копий.

### Режимы обновления

1. Полная перезагрузка.
    
2. Инкрементальное обновление.
    

Для инкрементального обновления предусматривается использование:

- Полей изменения записей (`updated_at` и аналогичных).
    
- Change Tracking.
    
- CDC.
    

Если надёжный механизм определения изменений отсутствует, используется полная перезагрузка.

### Scheduler

В MVP Scheduler поддерживает:

- Плановое обновление коллекций.
    
- Ручной запуск обновления.
    
- Выполнение обновлений по расписанию независимо от наличия изменений.
    

В последующих версиях Scheduler должен уметь предварительно определять наличие изменений и пропускать ненужное копирование.

### Группы синхронизации

Администратор может объединять коллекции в группы синхронизации.

Это позволяет управлять обновлением связанных наборов данных в рамках единого процесса.

### Обработка ошибок

При неудачном обновлении:

1. Система фиксирует ошибку.
    
2. Выполняет автоматические повторные попытки с увеличивающимися интервалами.
    
3. После исчерпания попыток сохраняет ошибку и ожидает следующего запуска.
    
4. Предыдущая успешная версия данных остаётся доступной.
    

## 9. Согласованность данных

В MVP при получении данных необходимо обеспечивать согласованный снимок источника на момент чтения, если это поддерживается используемой СУБД.

Для MS SQL Server и PostgreSQL механизмы получения согласованного снимка должны учитывать особенности транзакционной модели конкретного источника.

В дальнейшем механизм согласованности может настраиваться отдельно для каждого источника и сценария синхронизации.

## 10. Storage Engine и публикация данных

Storage Engine отвечает за:

- Запись Parquet.
    
- Чтение Parquet.
    
- Управление версиями локальных копий.
    
- Управление состоянием коллекций.
    
- Публикацию успешно обновлённых данных.
    

Основное требование: потребитель всегда получает последнюю успешно загруженную версию коллекции.

Обновление не должно приводить к выдаче частично записанных данных.

Предполагаемая модель:

1. Создание новой версии коллекции.
    
2. Получение и сохранение данных.
    
3. Проверка успешности операции.
    
4. Публикация новой версии.
    
5. Переключение API на актуальную версию.
    

При ошибке предыдущая версия остаётся доступной.

## 11. REST API

REST GET — единственный интерфейс потребления данных в MVP.

API автоматически формируется на основе опубликованных SQL VIEW и соответствующих коллекций.

### Основные возможности

- Получение коллекций.
    
- Фильтрация.
    
- Сортировка.
    
- Выбор отдельных полей.
    
- Пагинация.
    
- Вложенные AND/OR-условия.
    

### Пагинация

Поддерживаются два механизма:

**Offset pagination**

- `limit`.
    
- `offset`.
    

Используется для небольших выборок и простых сценариев.

**Cursor pagination**

- Получение следующей порции данных по курсору.
    
- Основной механизм для больших коллекций.
    
- Предпочтительный вариант при работе с сотнями миллионов записей.
    

### Ограничения MVP

Не предусматриваются:

- Произвольное выполнение SQL через REST API.
    
- Агрегации.
    
- JOIN между коллекциями.
    
- REST POST, PUT, PATCH и DELETE.
    

## 12. Аутентификация и авторизация

Для MVP используется OAuth 2.0 Client Credentials Flow.

### Регистрация клиента

Администратор регистрирует приложение-потребителя.

OpenDWH выдаёт:

- `client_id`.
    
- `client_secret`.
    

### Получение токена

Приложение использует свои учётные данные для получения access token.

Далее токен передаётся в REST API через Bearer Authorization.

### RBAC

Авторизация выполняется на уровне коллекций.

Администратор определяет:

- Какие клиенты существуют.
    
- Какие роли назначены клиентам.
    
- К каким коллекциям разрешён доступ.
    

Потребитель получает только те данные, на которые у него есть разрешение.

### Интеграция с AD

Взаимодействие с Active Directory предусматривается для корпоративной аутентификации и использования сервисных учётных записей при подключении к исходным СУБД, например Microsoft SQL Server.

## 13. Хранение секретов

В MVP секреты подключений хранятся в PostgreSQL в зашифрованном виде.

В последующих версиях предусматривается интеграция с корпоративными Secret Manager, например HashiCorp Vault.

Шифрование должно использовать ключ, который хранится отдельно от самой базы данных.

## 14. Ресурсные ограничения

В MVP администратор может задавать индивидуальные ограничения для источников и коллекций.

Предусматриваются:

- Максимальное количество параллельных синхронизаций.
    
- Ограничения нагрузки на исходные СУБД.
    
- Лимиты памяти для операций обработки данных.
    
- Таймауты.
    
- Ограничения REST API.
    

В дальнейшем вводится двухуровневая система:

- Глобальные ограничения OpenDWH.
    
- Индивидуальные ограничения источников и коллекций.
    

## 15. Наблюдаемость

Через CLI администратор должен иметь доступ к:

### Статусам

- Состояние источников.
    
- Состояние коллекций.
    
- Текущее состояние синхронизации.
    

### Истории операций

- Время начала.
    
- Время завершения.
    
- Длительность.
    
- Количество обработанных записей.
    
- Результат операции.
    

### Ошибкам

- Логи ошибок.
    
- Причины неудачных операций.
    
- Подробности выполнения синхронизации.
    

## 16. Основные архитектурные риски

1. **Производительность Parquet.** Выбор Query Engine существенно влияет на скорость REST API и потребление ресурсов.
    
2. **Инкрементальное обновление.** Не все SQL VIEW допускают надёжное определение изменений.
    
3. **Консистентность источников.** Получение согласованного снимка больших объёмов данных может создавать дополнительную нагрузку.
    
4. **Публикация коллекций.** Необходимо обеспечить атомарное переключение между версиями данных.
    
5. **Конкурентный доступ.** Single-node не отменяет необходимости контролировать параллельные REST-запросы и процессы синхронизации.
    
6. **Управление схемами.** Изменение исходного VIEW может нарушить совместимость существующих API.
    
7. **Безопасность секретов.** Компрометация PostgreSQL не должна автоматически раскрывать все учётные данные источников.

## 18. Архитектурный принцип

OpenDWH должна отделять источники данных от механизмов их хранения и потребления.

Исходная СУБД отвечает за предоставление корпоративных данных.

Connector Engine отвечает за получение данных.

Storage Engine отвечает за локальное хранение.

Query Engine отвечает за обработку запросов.

REST API предоставляет данные потребителям.

Scheduler управляет жизненным циклом обновления.

Администратор управляет всей системой через CLI.

**Основной принцип: один раз подключить корпоративные данные, централизованно управлять ими и многократно предоставлять потребителям через единый REST API.**
