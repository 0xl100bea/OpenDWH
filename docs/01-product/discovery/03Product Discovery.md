
## 1. Видение продукта

**OpenDWH** — On-Premise платформа для централизованного доступа к корпоративным данным через единый REST API.

Продукт предназначен для крупных организаций, работающих с разнородными информационными системами, legacy-СУБД и большими объёмами данных.

Основная задача OpenDWH — устранить необходимость создавать, настраивать и сопровождать отдельные интеграции для каждого приложения, BI-инструмента или автоматизации.

OpenDWH должен стать единым промежуточным слоем между корпоративными источниками данных и системами-потребителями.

Ключевые принципы:

- Производительность.
    
- Прозрачность работы с данными.
    
- Низкий порог входа для потребителей.
    
- Централизованное управление доступом.
    
- Контроль нагрузки на исходные системы.
    
- Полная автономность внутри инфраструктуры предприятия.
    

## 2. Целевая аудитория

Основные пользователи:

- Аналитики данных и BI-разработчики.
    
- Разработчики приложений и внутренних сервисов.
    
- Системные архитекторы.
    
- Интеграторы.
    
- Специалисты, занимающиеся автоматизацией бизнес-процессов.
    

Основной целевой сегмент — крупные предприятия с развитой IT-инфраструктурой, legacy-системами и значительными объёмами корпоративных данных.

Особенно актуален российский рынок, где многие организации продолжают использовать устаревшие информационные системы, не предоставляющие удобных современных интерфейсов для интеграции.

## 3. Проблема

Получение данных из корпоративных информационных систем часто требует отдельных подключений, согласований, сервисных учётных записей, разработки SQL-функций и участия DBA.

При этом разные потребители одних и тех же данных самостоятельно реализуют механизмы подключения и обработки.

Это приводит к:

- Дублированию интеграций.
    
- Зависимости разработчиков от DBA и владельцев информационных систем.
    
- Дополнительным согласованиям доступа.
    
- Сложностям сопровождения большого количества подключений.
    
- Повторной реализации одинаковой логики получения данных.
    
- Дополнительной нагрузке на production-системы.
    

Существующие инструменты частично решают эти задачи, однако требуют определённой технической подготовки и не всегда предоставляют единый, прозрачный механизм доступа к данным для разных категорий потребителей.

## 4. Продуктовая гипотеза

Если предоставить организации централизованную платформу, которая подключается к корпоративным СУБД, работает с контролируемыми SQL VIEW, создаёт локальные копии данных и автоматически предоставляет REST API, то потребители смогут получать необходимые данные без самостоятельной реализации отдельных интеграций.

Вместо множества прямых подключений к различным источникам организация получает единый управляемый слой доступа к данным.

## 5. Основная ценность

Главная ценность OpenDWH — сокращение времени между появлением потребности в данных и их фактическим использованием.

Потребителю не требуется разбираться в особенностях исходной СУБД, устанавливать драйверы, исследовать структуру таблиц или самостоятельно реализовывать механизм подключения.

REST API выступает стандартным интерфейсом взаимодействия.

Это снижает порог входа для разработчиков и аналитиков, сохраняя возможность эффективной работы с большими объёмами данных.

## 6. Размещение и безопасность

OpenDWH — исключительно On-Premise продукт.

Это фундаментальное архитектурное ограничение, а не временное решение для MVP.

Обязательные принципы:

- Развёртывание исключительно внутри инфраструктуры организации.
    
- Отсутствие зависимости от облачных сервисов.
    
- Отсутствие передачи корпоративных данных за пределы локального окружения.
    
- Хранение данных исключительно внутри инфраструктуры предприятия.
    
- Централизованное управление доступом через RBAC.
    
- Контролируемое взаимодействие с исходными СУБД.
    

Использование Cloud-инфраструктуры для размещения OpenDWH не входит в продуктовую концепцию.

## 7. Масштабируемость

Целевой масштаб продукта:

- Миллиарды записей.
    
- Терабайты данных.
    
- Большие корпоративные массивы информации.
    

При этом MVP должен ориентироваться на более умеренный масштаб: сотни миллионов записей и сотни гигабайт данных.

Архитектура должна предусматривать дальнейшее масштабирование без необходимости фундаментальной переработки продукта.

Поддержка целевого масштаба является долгосрочным требованием, а не подтверждённой характеристикой текущей реализации.

## 8. Основные роли

### Администратор

Отвечает за:

- Подключение источников данных.
    
- Настройку параметров подключения.
    
- Управление доступом.
    
- Настройку RBAC.
    
- Определение доступных SQL VIEW.
    
- Управление локальными копиями.
    
- Контроль процессов обновления данных.
    

### Потребитель данных

Отвечает за использование предоставленных ему наборов данных.

Получает доступ к необходимым коллекциям в рамках назначенных разрешений и использует автоматически сформированные REST API endpoints.

Потребитель не должен самостоятельно настраивать подключения к исходным СУБД.

## 9. Предполагаемый принцип работы

Базовый сценарий:

1. Администратор подключает корпоративную СУБД.
    
2. Определяет доступные SQL VIEW.
    
3. Настраивает параметры получения данных.
    
4. OpenDWH получает данные из исходной системы.
    
5. Данные сохраняются в локальном хранилище.
    
6. На основе доступных представлений формируются REST API endpoints.
    
7. Администратор назначает права доступа.
    
8. Потребители используют необходимые коллекции через REST API.
    

Предусматриваются два режима работы:

**Прямое чтение**

- Получение данных непосредственно из исходной СУБД.
    
- Использование контролируемых SQL VIEW.
    
- Возможность работы с актуальными данными без предварительного копирования.
    

**Локальные копии**

- Получение данных из исходной СУБД.
    
- Сохранение данных в локальном хранилище OpenDWH.
    
- Предоставление доступа через REST API без необходимости обращаться к production при каждом запросе.
    
- Плановое обновление копий.
    

## 10. Границы MVP

### Обязательные возможности

1. Подключение к нескольким типам СУБД:
    
    - Microsoft SQL Server.
        
    - PostgreSQL.
        
2. Работа с SQL VIEW в исходных базах данных.
    
3. Создание локальных копий данных.
    
4. Планирование обновлений через cron.
    
5. Поддержка двух механизмов обновления:
    
    - Полная перезагрузка.
        
    - Инкрементальное обновление.
        
6. Контроль нагрузки на исходную СУБД во время получения данных.
    
7. Автоматическая генерация REST API на основе SQL VIEW.
    
8. Синхронизация API с состоянием локальных копий.
    
9. Управление доступом через RBAC.
    
10. CLI как основной интерфейс управления на этапе MVP.
    

### За пределами MVP

- Web-интерфейс администратора.
    
- Поддержка дополнительных типов СУБД.
    
- Расширенные инструменты мониторинга.
    
- Дополнительные механизмы масштабирования.
    
- Расширенные средства управления инфраструктурой.
    

## 11. Критерии успеха

Главный критерий успеха — получение и обработка необходимых данных за секунды вместо длительной бюрократической и технической рутины.

Практические признаки успешной реализации:

- Подключение нового источника не требует разработки отдельного интеграционного приложения.
    
- Потребитель может получить необходимые данные через REST API.
    
- Для доступа к данным не требуется самостоятельно устанавливать драйверы и исследовать структуру исходной СУБД.
    
- Разные приложения и BI-инструменты используют единый промежуточный слой.
    
- Локальные копии позволяют сократить количество обращений к production.
    
- Администратор централизованно управляет доступом и обновлением данных.
    

## 12. Основные продуктовые ограничения

1. Только On-Premise.
    
2. Никаких облачных зависимостей.
    
3. Никакого хранения корпоративных данных за пределами локальной инфраструктуры.
    
4. REST API — основной интерфейс взаимодействия с потребителями.
    
5. SQL VIEW — основной механизм определения доступных наборов данных на стороне источника.
    
6. Контроль нагрузки на production — обязательное требование.
    
7. CLI — основной интерфейс MVP.
    

## 13. Долгосрочное видение

OpenDWH должен стать универсальным промежуточным слоем доступа к корпоративным данным.

В идеальной модели организация подключает свои информационные системы к OpenDWH один раз, после чего различные потребители используют единый механизм получения данных.

Это позволяет сократить количество самостоятельных интеграций, уменьшить зависимость от особенностей legacy-систем и упростить разработку внутренних приложений, автоматизаций и аналитических решений.

**Главная идея: один раз подключить данные — многократно использовать их через единый интерфейс.**
