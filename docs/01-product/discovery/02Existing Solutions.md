
## 1. Цель исследования

Цель данного этапа — изучить существующие подходы и инструменты для решения проблем, выявленных в Problem Discovery.

Основные задачи исследования:

- Определить, какие существующие решения закрывают потребности в подключении к корпоративным БД и извлечении данных.
    
- Изучить механизмы локального хранения и синхронизации данных.
    
- Оценить возможности предоставления данных внешним потребителям через API.
    
- Выявить ограничения существующих решений применительно к предполагаемым сценариям использования OpenDWH.
    

Исследование не ставит целью составление полного каталога DWH- и ETL-платформ.

## 2. Подходы, использовавшиеся на практике

В организации отсутствовало централизованное решение для получения и предоставления данных из корпоративных информационных систем. Сотрудники самостоятельно выбирали инструменты и выстраивали процессы интеграции под конкретные задачи.

### 2.1. Qlik Sense / QVD

Использовался механизм создания бинарных снимков данных по SQL-запросам средствами Qlik Sense.

Полученные QVD-файлы использовались для последующей обработки, в том числе через библиотеку pyqvd.

Ограничения:

- QVD является проприетарным форматом экосистемы Qlik.
    
- Работа с файлами через pyqvd требовала загрузки всего набора данных в оперативную память.
    
- Обработка больших объёмов данных занимала значительное время.
    
- Использование сетевых папок создавало дополнительную зависимость от стабильности сетевого соединения.
    
- Инструменты работы с форматом были привязаны к конкретным языкам программирования и экосистеме.
    

### 2.2. ETL / Windmill

Рассматривался подход с использованием Windmill для автоматизации извлечения и сохранения данных.

В рамках конкретной реализации процесс представлял собой выполнение скриптов, которые получали данные из источника и сохраняли их в целевую систему.

Ограничения:

- Отсутствие единого целостного механизма управления процессом получения и хранения данных.
    
- Необходимость самостоятельно обеспечивать корректность и согласованность результатов.
    
- Появление дополнительных инфраструктурных зависимостей.
    
- Для организации хранения и передачи данных требовалось подключать внешние компоненты, например S3-совместимое хранилище.
    

### 2.3. SQL-клиент, драйверы и табличные функции

Наиболее практичным оказался вариант непосредственного подключения к production-БД через SQL-клиент и драйверы с использованием заранее подготовленных табличных функций.

Пример получения информации о сотруднике из ERP:

```
SELECT getemployee(tab);
```

Где `tab` — табельный номер сотрудника.

Полученные данные сохранялись в локальную БД.

Преимущества:

- Относительно быстрое подключение к источнику после получения необходимых разрешений.
    
- Возможность получать более актуальные данные без необходимости ожидать обновления отдельного снимка.
    
- Предсказуемая работа подготовленных табличных функций.
    

Ограничения:

- Для первоначального подключения требовалась сервисная учётная запись и согласование доступа.
    
- Структура production-БД была недоступна разработчикам для самостоятельного исследования.
    
- Legacy-системы практически не имели документации, поэтому требования к выборкам формировались на основании бизнес-потребностей.
    
- При необходимости расширить выборку или создать новую функцию требовалось повторное взаимодействие с DBA и владельцами информационных систем.
    
- Большие объёмы данных и разнообразие задач приводили к постоянной необходимости создавать новые табличные функции.
    

Основные издержки возникали не при непосредственном получении данных, а на этапах определения необходимых данных, согласования и подготовки механизмов доступа.

## 3. Существующие программные решения

### 3.1. Data Integration / ETL

#### Airbyte

Официальный сайт: [https://airbyte.com/](https://airbyte.com/)

Airbyte — платформа интеграции данных, предназначенная для переноса информации между различными источниками и хранилищами.

Основные возможности:

- Подключение к различным источникам данных через коннекторы.
    
- Полная и инкрементальная синхронизация.
    
- Выполнение синхронизации по расписанию.
    
- Обработка изменений структуры данных.
    
- Управление процессами извлечения и загрузки.
    

Потенциальная применимость к OpenDWH:

Airbyte закрывает значительную часть задач автоматизированного извлечения и переноса данных. Однако он не ориентирован на предоставление универсального REST API конечным потребителям и не устраняет необходимость предварительного определения требуемых данных и организации доступа к источникам.

### 3.2. CDC / Replication

#### Debezium

Официальный сайт: [https://debezium.io/](https://debezium.io/)

Debezium — платформа Change Data Capture, предназначенная для отслеживания изменений в базах данных и передачи событий потребителям.

Основные возможности:

- Отслеживание INSERT, UPDATE и DELETE.
    
- Получение изменений из журналов транзакций поддерживаемых СУБД.
    
- Передача событий через Kafka Connect.
    
- Первоначальная загрузка снимков данных.
    
- Поддержание локальных копий в актуальном состоянии.
    

Потенциальная применимость к OpenDWH:

Debezium может использоваться для реализации механизмов синхронизации и обновления локальных копий данных.

При этом он не является универсальным API-слоем и не решает задачи публикации произвольных SQL-представлений в виде REST endpoints.

### 3.3. SQL Federation / Data Virtualization

#### Trino

Официальный сайт: [https://trino.io/](https://trino.io/)

Trino — распределённый SQL-движок, позволяющий выполнять запросы к различным источникам данных через единый интерфейс.

Основные возможности:

- Подключение к разнородным источникам.
    
- Выполнение распределённых SQL-запросов.
    
- Объединение данных из нескольких систем.
    
- Работа с источниками без обязательного предварительного копирования данных.
    

Потенциальная применимость к OpenDWH:

Trino может выступать единым SQL-слоем для доступа к различным корпоративным БД.

Однако он не ориентирован на автоматическое создание локальных копий и REST API для прикладных потребителей в качестве единого сценария.

### 3.4. REST API over SQL

#### PostgREST

Официальный сайт: [https://postgrest.org/](https://postgrest.org/)

PostgREST автоматически предоставляет REST API на основе структуры PostgreSQL.

Основные возможности:

- Публикация таблиц и представлений через REST API.
    
- Преобразование функций PostgreSQL в RPC endpoints.
    
- Использование ролевой модели доступа PostgreSQL.
    
- Автоматическая генерация OpenAPI-описания.
    

Потенциальная применимость к OpenDWH:

PostgREST представляет особый интерес из-за механизма публикации SQL-представлений и функций через REST API.

Однако решение ориентировано на PostgreSQL и не предоставляет универсального механизма подключения к произвольным внешним СУБД с последующей материализацией данных.

### 3.5. Analytical Storage / DWH

#### ClickHouse

Официальный сайт: [https://clickhouse.com/](https://clickhouse.com/)

ClickHouse — аналитическая СУБД, предназначенная для хранения и обработки больших объёмов данных.

Основные возможности:

- Высокопроизводительная аналитическая обработка.
    
- Хранение больших наборов данных.
    
- Интеграция с внешними источниками.
    
- Получение данных через SQL-интерфейс.
    
- Предоставление данных через HTTP-интерфейс.
    

Потенциальная применимость к OpenDWH:

ClickHouse может выступать локальным хранилищем данных, позволяя перенести нагрузку с production-БД на отдельную инфраструктуру.

При этом ClickHouse самостоятельно не решает все задачи управления подключениями, определения необходимых выборок и организации API для разных источников.

### 3.6. Workflow Orchestration

#### Windmill

Официальный сайт: [https://windmill.dev/](https://windmill.dev/)

Windmill — платформа автоматизации и оркестрации процессов с поддержкой выполнения скриптов на разных языках программирования.

Основные возможности:

- Выполнение скриптов.
    
- Создание последовательностей задач и workflows.
    
- Управление подключениями и секретами.
    
- Планирование выполнения задач.
    
- Мониторинг и обработка ошибок.
    
- Организация ETL-процессов.
    

Потенциальная применимость к OpenDWH:

Windmill может использоваться для автоматизации извлечения и обработки данных.

Однако он не является специализированным решением для централизованного управления доступом к корпоративным данным и предоставления унифицированного API.

## 5. Предварительные выводы

Рассмотренные решения преимущественно специализируются на отдельных этапах работы с данными:

- Airbyte — извлечение и перенос данных.
    
- Debezium — отслеживание и передача изменений.
    
- Trino — единый SQL-доступ к различным источникам.
    
- PostgREST — предоставление REST API над PostgreSQL.
    
- ClickHouse — локальное хранение и аналитическая обработка.
    
- Windmill — автоматизация и оркестрация процессов.
    

При этом отдельные инструменты уже предоставляют значительную часть функциональности, которая рассматривается для OpenDWH.

Потенциальная область продукта находится на пересечении нескольких направлений:

1. Централизованное подключение к разнородным корпоративным БД.
    
2. Получение данных через контролируемые SQL-представления.
    
3. Сохранение выбранных наборов данных в локальном хранилище.
    
4. Автоматизированное предоставление REST API.
    
5. Централизованное управление доступом потребителей.
    

Наличие отдельных инструментов для каждой из этих задач ещё не доказывает необходимость создания нового продукта. Необходимо дополнительно проверить, насколько существующие платформы позволяют объединить перечисленные возможности без существенного усложнения эксплуатации.

## 6. Ограничения исследования

Исследование является предварительным.

Рассмотрены наиболее релевантные категории инструментов, но не проведено полноценное тестирование каждого решения.

Необходимо отдельно изучить платформы, которые могут объединять несколько перечисленных возможностей:

- Hasura.
    
- NocoDB.
    
- Directus.
    

Также требуется проверить, существуют ли готовые решения, предоставляющие единый интерфейс для подключения к разнородным источникам, материализации данных и генерации REST API.

## 7. Итог

На текущем этапе не выявлено оснований утверждать, что OpenDWH не имеет аналогов или что его предполагаемая функциональность уникальна.

Однако исследование показывает возможность объединить несколько разрозненных механизмов в единый продукт, ориентированный на упрощение доступа к корпоративным данным для аналитиков и разработчиков.

Дальнейшее исследование должно определить, действительно ли такое объединение решает самостоятельную пользовательскую проблему и оправдывает создание отдельного продукта.
