## Обзор

Документ фиксирует, что известно о пользователях OpenDWH на текущий момент, и разделяет это на подтверждённые знания и гипотезы. Источник знаний — личный опыт автора в одной организации [ФАКТ: выборка n=1] и сегменты, названные в `03Product Discovery`.

[ФАКТ] Контекст проекта: OpenDWH — личный некоммерческий проект автора (цели: изучить Rust и архитектуры приложений). Пользовательские знания на этом этапе основываются только на опыте автора; интервью на текущем этапе не проводятся.

## 1. Что уже известно

[ФАКТ] Из `03Product Discovery` (§2, §8):

- Основные пользователи: аналитики данных и BI-разработчики; разработчики приложений и внутренних сервисов; системные архитекторы; интеграторы; специалисты по автоматизации бизнес-процессов.
- Роли в продукте: **Администратор** (подключает источники, управляет доступом и обновлениями) и **Потребитель данных** (работает с коллекциями через REST API).
- Целевой сегмент: крупные предприятия с legacy-системами; особенно актуален российский рынок.

[ФАКТ] Из `01Problem Discovery`: реальные боли наблюдались со стороны аналитика/разработчика — получение доступа к данным занимало дни и зависело от смежных подразделений.

[ФАКТ, ответ автора 2026-11-23] Gatekeepers внедрения — DBA и владельцы ИС: именно они страдают от обращений за доступом к production. Информационная безопасность заинтересована в продукте: централизация даёт предметный контроль над сервисными УЗ и активностью.

[РЕШЕНИЕ, подтверждено автором 2026-11-23] REST API — единственный интерфейс потребления данных, в том числе для BI (Superset, Qlik Sense, DataLens). Нативная работа BI-инструментов с REST как источником данных — реализуемость требует проверки прототипом (спайк).

## 2. Персоны (черновые, не проверены)

### Персона А — «Аналитик данных» [ГИПОТЕЗА]

- Работает в BI (Qlik/Power BI/Tableau), строит отчётность по данным нескольких корпоративных систем.
- Боль: нужна таблица из ERP/СЭД, а это недели согласований; делает «костыли» через выгрузки.
- Ценность OpenDWH: REST API или готовые коллекции вместо прямого доступа к production.
- Технический уровень: SQL на уровне выборок, программирование — базовое.

### Персона Б — «Разработчик внутренних сервисов» [ГИПОТЕЗА]

- Пишет небольшие приложения автоматизации (справочники, уведомления, интеграции).
- Боль: каждая новая выборка из legacy-БД — новая табличная функция и взаимодействие с DBA; контракты нестабильны.
- Ценность OpenDWH: стабильный REST API, не думает о драйверах, схемах и согласованиях.
- Технический уровень: уверенный, REST/JSON — родная среда.

### Персона В — «Администратор платформы» [ФАКТ: роль подтверждена; детали — опыт одной организации]

- DBA или владелец ИС, которому делегируют владение OpenDWH.
- Боль: постоянные обращения аналитиков и разработчиков за доступом к production — лишняя нагрузка на продуктивные БД.
- Ценность OpenDWH: централизованный контроль, RBAC, лимиты нагрузки, предметная регуляция сервисных УЗ [ФАКТ: ИБ «за»].
- Это gatekeeper внедрения: без его согласия продукта в организации не будет.

## 3. Сценарии использования (JTBD)

- Когда аналитику нужна новая витрина данных, он хочет получить её через REST API за часы, а не недели согласований.
- Когда разработчику нужны данные справочника в приложении, он хочет стабильный endpoint с документацией, а не SQL-функцию, которая может измениться.
- Когда DBA получает очередной запрос на доступ к production-БД, он хочет заменить выдачу прямого доступа доступом к OpenDWH [ФАКТ].
- Онлайн-доступ к данным нужен редко — в основном инциденты с максимальным простоем ~30 минут, когда все обращаются к проду напрямую (пример: данные биллинга → Zabbix) [ФАКТ]. Вывод: режим «прямого чтения» из `04Product Architecture` §9 обоснован, но не является сценарием MVP.
