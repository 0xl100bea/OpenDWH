# Problem Discovery

Тип: concept. Статус: accepted. Дата: 2026-11-24.

Документ описывает проблему, на решение которой направлен OpenDWH: как она наблюдается, из каких областей состоит, чем ограничена. Видение и ценность продукта — в `01-Product Discovery.md`, анализ существующих решений — в `03-Existing Solutions.md`.

## 1. Источник наблюдений

Описание проблемы составлено на основе двух источников:

- массива публичных обсуждений (форумы, сообщества аналитиков и разработчиков) о работе с корпоративными данными;
- профессионального опыта автора в одной из республиканских телекоммуникационных организаций РФ в роли старшего аналитика — как одного из представительных кейсов.

Опыт автора используется для конкретизации, а не как единственное основание выводов.

## 2. Формулировка проблемы

Получение данных из корпоративных информационных систем для аналитики и малой автоматизации сегодня идёт по двум фронтам, оба неприемлемы:

1. **Прямое подключение к production** с выполнением произвольных SQL-запросов — с риском нарушить стабильность продуктивной системы и нарушением требований информационной безопасности.
2. **Временные выгрузки** (файлы, QVD и подобное) — нарушающие требования управляемости данных: неясное происхождение, неактуальность, отсутствие контроля распространения.

Между этими фронтами организации выбирают преимущественно второй: выгрузка из ИС занимает от 5 минут до 2 часов, не требует развёртывания инфраструктуры и привычных инструментов (Python, pandas, openpyxl). Команды с более высокой технической зрелостью пытаются перейти на подключение через табличные функции SQL, однако это сдвигает проблему, а не решает её (см. §4.4).

Проблема возникает ежедневно.

## 3. Масштаб

В контуре одного аналитика одновременно существуют десятки источников данных. Реальная карта одного наблюдаемого контура:

- ERP — Microsoft SQL Server;
- СЭД — Microsoft SQL Server;
- биллинг — Oracle;
- микросистемы организации — Oracle, PostgreSQL;
- собственные системы автоматизации — PostgreSQL, MySQL.

Параллельно существуют десятки временных файлов-выгрузок у одного аналитика; на уровне организации — сотни или тысячи.

Срок актуальности выгрузки определяется природой данных: для биллинга, где данные обновляются ежесекундно, выгрузка устаревает в течение часа; для более стабильных направлений — днями. При ручном сопровождении файлов обновление занимает рабочие дни, а человеческий фактор добавляет ошибки в данные.

## 4. Проблемные области

### 4.1. Организационная зависимость при получении доступа

Подключение к новому источнику требует последовательного участия владельцев ИС, DBA и информационной безопасности: сервисные учётные записи, привилегии, сетевой доступ, объекты БД, проверки ИБ. Полный цикл «появилась потребность в новом источнике → можно работать с данными» занимает в среднем 1,5 дня (от пары часов до нескольких рабочих суток) и зависит от доступности сотрудников смежных подразделений.

### 4.2. Неизученность источников

Внутренние ИС зачастую построены на legacy-БД с недостаточной документацией. Назначение таблиц, полей и связей не очевидно, предварительное исследование структуры проводится без полноценного доступа к данным, что увеличивает ручные операции и вероятность ошибок.

### 4.3. Устаревание локальных копий

Локальные копии и выгрузки поддерживаются вручную: обновление занимает рабочие дни, содержит ошибки ручного ввода, а актуальность деградирует с разной скоростью в зависимости от данных — от часа для операционных массивов.

### 4.4. Нестабильность механизмов интеграции

Стандартизированный API у корпоративных ИС обычно отсутствует. Табличные функции SQL как «продвинутый» механизм не закрывают проблему:

- выпускать и изменять функцию может только DBA — зависимость от смежных отделов сохраняется;
- вызов табличной функции из кода — это по сути произвольный SQL, открывающий риск SQL-инъекций при отсутствии политик безопасности;
- при отсутствии готовой функции разработчик с доступом к prod пишет собственные запросы, что приводит к обрушениям продуктивной системы из-за нагрузки.

### 4.5. Риски информационной безопасности

Используемая инфраструктура содержит устойчивые риски: сервисные учётные записи без срока действия, подключения без шифрования внутри локальной сети, прямой сетевой доступ от рабочих сред разработки к продуктивным БД, рост количества точек подключения к критическим системам.

### 4.6. Отсутствие управляемости данных

Временные файлы лишены управляемости по построению: их происхождение не отслеживается (невозможно отличить выгрузку из ИС от самостоятельно созданного документа), версии не различаются (параллельные копии вида `billing_ALL_FINAL_FINAL_F2.xlsx` у разных сотрудников могут расходиться и при этом считаться каждая «финальной»), распространение не контролируется.

### 4.7. Новые риски эпохи ИИ

Возник самостоятельный драйвер проблемы: сотрудники без компетенций в информационной безопасности подключают ИИ-агентов напрямую к базам данных, содержащим персональные и иные чувствительные данные. Для организации это критический риск, прямо следствие отсутствия контролируемого промежуточного слоя доступа к данным.

## 5. Границы проблемы

Проблема не возникает или терпима в ограниченных случаях:

- ИС имеет готовый API для предоставления массивов данных — по наблюдениям, редкость;
- данные целиком находятся внутри средств малой автоматизации под собственным контролем аналитика;
- федеральные ИС с ограниченным и стабильным пулом данных, где разовая выгрузка оправдана.

За этими границами существующие процессы достаточно хороши, и OpenDWH не ставит целью их замену.

## 6. Непокрытая потребность

Существует потребность в едином, контролируемом и стандартизированном механизме предоставления данных из внутренних информационных систем аналитикам и разработчикам. Такой механизм должен снижать необходимость индивидуальных подключений к каждой продуктивной БД, уменьшать зависимость проектов от ручных операций смежных подразделений, обеспечивать предсказуемость получения данных и управляемость их происхождения, актуальности и доступа.

## 7. Ограничения исследования

Выводы основаны на массиве публичных обсуждений и одном организационном кейсе автора. Не подтверждено, насколько описанная совокупность проблем характерна для других отраслей; требуют дополнительной проверки распространённость проблемы среди аналитических и IT-команд, экономические последствия существующих процессов и готовность организаций менять устоявшиеся практики.
