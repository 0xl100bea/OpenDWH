# Product Discovery

Тип: concept. Статус: accepted. Дата: 2026-11-24.

OpenDWH — открытый проект. Назначение и границы документа: видение продукта, цели, аудитория, ценность и продуктовая гипотеза. Проблема детально — в `02-Problem Discovery.md`, существующие решения — в `03-Existing Solutions.md`, механика и ограничения — в `04-Product Architecture.md`.

## 1. Видение продукта

**OpenDWH** — открытая (open source) система класса Data Warehouse, предназначенная для помощи организациям в развитии аналитики и малой автоматизации.

Продукт реализуется как on-premise платформа централизованного доступа к корпоративным данным через единый API. Она устраняет необходимость создавать, настраивать и сопровождать отдельные интеграции для каждого приложения, BI-инструмента или сценария автоматизации.

Ключевые принципы:

- Открытость: код открыт, проект развивается под эгидой сообщества.
- Централизованный подход: единый промежуточный слой между корпоративными источниками данных и их потребителями.
- Единый интерфейс доступа к данным для всех категорий потребителей.
- Автономность: развёртывание и работа полностью внутри инфраструктуры организации.

## 2. Цели проекта

1. **Практическая цель** — инструмент для решения собственных задач автора: получение и работа с качественными, согласованными данными из корпоративных систем без обходных решений и рисков для production.
2. **Проектная цель** — open source продукт, доступный всем. Проект не закрывается под лицензирование одной организации и развивается под направлением сообщества.

Цели не конфликтуют: собственные задачи служат источником эталонных сценариев, сообщество — драйвером развития и проверкой применимости за пределами одной организации.

### Приоритеты при конфликтах

При конфликте между скоростью выхода MVP, глубиной функциональности и качеством/надёжностью приоритет отдаётся глубине функциональности и качеству/надёжности.

### Критерии успеха

- **Личный критерий**: задачи в различных организациях выполняются в полной мере — данные получаются и используются без обходных решений и рисков для prod.
- **Критерий сообщества**: звёзды репозитория и вопросы пользователей как показатели реального использования.

## 3. Целевая аудитория и сегмент

Основной сегмент — крупные предприятия с развитой IT-инфраструктурой, наличием legacy-систем и разнородных информационных систем на разных СУБД. Особенно актуален рынок РФ/СНГ, где организации продолжают эксплуатировать устаревшие системы без современных интерфейсов интеграции.

Первый пользователь в организации — администратор баз данных / администратор информационных систем: именно он выстраивает политики работы с первоисточниками и подключает OpenDWH к production. Потребитель данных — любой, кому нужны данные: аналитик, разработчик, BI-инженер, специалист по автоматизации.

Риск внедрения: препятствием становится любой участник без необходимых компетенций; наиболее вероятный сдерживающий фактор — DBA, чьё участие критично на старте. Это учитывается в проектировании опыта администратора.

## 4. Проблема (кратко)

Сегодня получение данных из корпоративных систем идёт по двум фронтам, оба неприемлемы:

1. Прямое подключение к production с выполнением произвольных SQL-запросов — с риском нарушить стабильность продуктивной системы.
2. Временные решения в виде выгрузок, QVD и подобного — нарушающие политику чистых данных и устаревающие быстро.

Проблема возникает ежедневно. Подробное описание — в `02-Problem Discovery.md`.

## 5. Основная ценность

**Доступ к корпоративным данным без обходных решений и без риска для prod.**

Потребитель не реализует собственные подключения к исходным системам; организация получает управляемый, безопасный и предсказуемый способ предоставления данных.

## 6. Продуктовая гипотеза

Если организация развёртывает централизованную платформу, которая подключается к корпоративным СУБД и предоставляет данным единый управляемый интерфейс, то потребители смогут получать необходимые данные без самостоятельной реализации отдельных интеграций — без обходных решений на стороне production и без временных выгрузок.

Механика реализации гипотезы (источники, способы получения данных, формат API) определяется в `04-Product Architecture.md` и проверяется спайками.

## 7. Эталонный сценарий

Крупная legacy ERP (пример: Microsoft Dynamics AX / Axapta), в которой живёт значительное количество организаций в РФ/СНГ. В организации существует потребность в малых автоматизациях для ускорения работы, однако из-за отсутствия интерфейсов управления данными реализация интеграционных сценариев невозможна. OpenDWH должен открыть доступ к данным такой системы для автоматизаций и аналитики.

Этот сценарий является приёмочным для MVP: если OpenDWH работает на таком кейсе, гипотеза считается подтверждённой.

## 8. Основные роли (на уровне продукта)

- **Администратор** — на этапе MVP это администратор БД/ИС. Подключает источники, выстраивает политики работы с первоисточниками, управляет доступом и обновлением данных.
- **Потребитель данных** — любой, кому нужны данные. Работает только через предоставленный интерфейс, не настраивает подключения к исходным СУБД.

## 9. Долгосрочное видение

OpenDWH — универсальная открытая точка доступа к корпоративным данным, развиваемая сообществом. Организация подключает свои информационные системы один раз, после чего различные потребители используют единый механизм получения данных.

**Главная идея: один раз подключить данные — многократно использовать их через единый интерфейс.**
